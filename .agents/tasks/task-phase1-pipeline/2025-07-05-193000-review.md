# Phase 1 production pipeline: topic-to-export orchestration

This PR introduces the full Phase 1 video production system — a `produce.py` CLI that orchestrates nine sequential stages from topic research through final video export. Each stage is a separate module under `pipeline/stages/`, inheriting from a `StageRunner` base class that handles input validation, output validation, and status tracking via `status.yaml`. The LLM abstraction (`pipeline/llm.py`) supports OpenAI-compatible APIs and falls back to structured placeholder output when no key is configured, allowing the pipeline to run end-to-end in test environments. The PR also adds ruff configuration to `pyproject.toml`, fixes pre-existing linting issues in scaffold code, and includes 60 pytest tests.

**Watch for:** The voice stage catches `SystemExit` and mutates `self.expected_outputs` at runtime, creating a race between the fallback path and the base class output validation (confirmed). The `find_video_folder` function matches any existing folder containing the slug substring, which can collide with unrelated folders (confirmed). The pipeline creates a new OpenAI client on every single `generate()` call with no connection reuse (confirmed).

## High-level view

The pipeline orchestration in `produce.py` is a straightforward sequential runner: resolve or create the video folder, load the stage registry, slice by `--from`/`--only`, and execute in order. The design is intentionally simple — no parallelism, no DAG, no retry. Each stage stops the pipeline on failure, and `status.yaml` records what completed so the user can resume with `--from`.

The stage abstraction (`StageRunner`) separates concerns cleanly: declare inputs/outputs as relative paths, implement `run()`, and the base class handles lifecycle. The trade-off is that tool-based stages (voice, subtitles, render, export) need dynamic validation and override the base class methods, which undermines the uniformity the abstraction provides.

The LLM layer is deliberately minimal — a single `generate()` function dispatching to OpenAI or placeholders. The placeholder mode maps system prompts to canned outputs via substring matching, which is brittle but functional for testing. The real concern is that prompt construction lives entirely in each stage module with no shared structure, so prompt quality will drift as stages evolve independently.

The test suite exercises CLI parsing, stage lifecycle, status tracking, and placeholder detection. It does not test tool-based stages (voice, subtitles, render, export) beyond interface checks, leaving the riskiest integration points uncovered.

<summary>Issues (6)</summary>

1. **Voice stage mutates expected_outputs at runtime** — When Kokoro fails and Edge-TTS succeeds with `.mp3`, the `run()` method sets `self.expected_outputs = ["voice/voiceover.mp3"]`, but the custom `validate_output()` already handles both extensions. The mutation is dead code that could confuse future maintenance or break if the base class is called. Remove the mutation line.
2. **Folder matching uses substring containment** — `find_video_folder` matches `slug in item.name`, so a topic "Air" would match a folder named "001_airplanes_dont_fall". Use exact slug suffix matching after stripping the numeric prefix.
3. **New OpenAI client per call** — `_call_api` instantiates `OpenAI(...)` on every invocation. For a 9-stage pipeline with potential multi-call stages, this creates unnecessary connection overhead. Consider module-level client caching or a lazy singleton.
4. **Prompt construction has no validation** — AI stages assemble prompts from file contents (research YAML, script markdown) with no size guards. A large research file or script could exceed model context limits silently, producing truncated or degraded output.
5. **Tool-based stages untested in integration** — Voice, subtitles, render, and export stages are not exercised in tests because their dependencies (Kokoro, Edge-TTS, faster-whisper, Manim, FFmpeg) are unavailable. Consider lightweight mocks that verify the stage wiring without requiring the full toolchain.
6. **Render stage has empty expected_outputs** — `RenderStage.expected_outputs = []` means the base class `validate_output()` always returns True. The custom override compensates, but the empty list is misleading and breaks the contract the base class documents.

## Voice stage fallback and output mutation

The `VoiceStage.run()` method catches `SystemExit` from `generate_with_kokoro` and falls back to `generate_with_edge_tts`. During the fallback, it mutates `self.expected_outputs = ["voice/voiceover.mp3"]`. This mutation is unnecessary because `validate_output()` is overridden to check for either `.wav` or `.mp3` directly — the base class `validate_output()` is never called. The mutation creates a subtle inconsistency: if a future refactor removes the custom `validate_output()`, the class-level `expected_outputs` (still `["voice/voiceover.wav"]`) won't reflect the runtime change for other instances.

More broadly, catching `SystemExit` is unusual. Both `generate_with_kokoro` and `generate_with_edge_tts` raise `SystemExit(1)` on import failure, not a normal exception. This means any `sys.exit()` call within those functions (including from deep dependencies) will be silently swallowed and treated as "engine unavailable." A tighter contract would have the voiceover module raise a specific exception type instead of calling `sys.exit`.

## Folder resolution collision

`find_video_folder` iterates `VIDEOS_DIR` and returns the first folder where `slug in item.name`:

```python
slug = slugify(topic)
for item in VIDEOS_DIR.iterdir():
    if item.is_dir() and slug in item.name:
        return item
```

This substring match means "AI" matches "001_airplanes_dont_fall", and "python" matches "002_python_is_everywhere". The intended behavior is to find an existing folder for the *same* topic, but the matching is too loose. A safer approach: strip the numeric prefix, compare the full slug equality.

## LLM client lifecycle and prompt boundaries

Each `generate()` call constructs a fresh `OpenAI` client. For a pipeline producing a single video this is fine operationally, but it means no HTTP connection reuse across stages. If any stage makes multiple LLM calls (not the case today, but likely for retry or refinement loops), the overhead compounds.

The prompt construction in each stage concatenates file contents directly into the user message with no token counting or truncation. The research stage asks for "4-6 facts" but doesn't enforce output length. The script stage includes the entire `prompts/script_writer.md` template inline. For a real LLM call, these prompts could approach context limits with verbose research or long templates. No stage checks whether the assembled prompt fits within the model's context window.

## Stage contract violations in tool-based stages

The `StageRunner` base class documents a contract: declare `required_inputs` and `expected_outputs`, and the lifecycle handles validation. But several tool-based stages break this:

- `SubtitlesStage`: `required_inputs = []` with a custom `validate_input()` override
- `RenderStage`: `expected_outputs = []` with a custom `validate_output()` override
- `ExportStage`: `required_inputs = []` with a custom `validate_input()` override

This isn't wrong — the overrides work — but it means the declarative lists are unreliable as documentation. A reader checking `required_inputs` to understand stage dependencies gets incomplete information for half the pipeline.

## Test coverage gaps

The test suite is solid for the AI stages and CLI mechanics. What's missing:

- No tests verify that tool-based stages (voice, subtitles, render, export) correctly call the underlying pipeline modules, even with mocks.
- No test exercises the full `produce.py` pipeline end-to-end (even with placeholder LLM and mocked tools) to verify that stage outputs chain correctly as inputs.
- The `find_video_folder` substring collision described above is not tested.
- No test covers the case where `generate()` has an API key set but the API call fails (network error, rate limit, invalid key).
